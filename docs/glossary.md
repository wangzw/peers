# Glossary

| Term | Definition |
|---|---|
| Broker | The daemon that runs on a host: it registers the local agents it serves, maintains links with peers, and writes received messages into the inbox socket of a local session. Each instance has its own fingerprint, peers and configuration; one host may run several instances, which by deployment form are a system Broker or a user Broker. |
| system Broker | A Broker that runs as a system service with privileges; a host has at most one, and it serves agents under the accounts permitted to use it on that host. |
| user Broker | A Broker that runs under an ordinary account and serves only agents of the same account. An account runs at most one instance. |
| agent | A Claude Code session that has enabled this system's tools and has registered with a Broker on its host, distinguished by that session's inbox socket. The session name, once normalized, must be non-empty and contain neither `@` nor `*`; that is a precondition for registration. A session that has not enabled the tools is not an agent. |
| remote agent | An agent registered with another Broker. |
| agent address | The string that locates an agent, made up in order of the agent's name, a disambiguator when needed, `@`, and the alias; the name is shortened when it does not fit. The alias is the one the Broker of the party seeing the address uses for the Broker that hosts the agent, so one agent can have different addresses on different Brokers. |
| disambiguator | A short identifier that distinguishes the agents on one Broker, computed from the session's inbox socket path by the same algorithm Claude Code uses to display that identifier in its session list. It is unique within a Broker and stays the same after the session is renamed or its conversation is cleared. |
| MCP server process | The child process Claude Code starts for a session that has enabled this system's tools; it starts with the session, provides tools to the session's model, and registers its session with the local Broker. |
| session registry | The record Claude Code keeps on the local host for each session process, holding the process id, the session name, the status and the location of the inbox socket; it is deleted when the session process exits. |
| inbox socket | The local socket Claude Code binds for each session, through which other processes deliver messages to that session. |
| inbound controls | The mechanism Claude Code applies to cross-session messages entering a session, deciding whether a message goes to the model, waits for user approval or is dropped. Its setting is called the inbound policy. |
| topic | A named scope of visibility and communication permission. Two agents can see each other and exchange messages only when they share at least one topic. |
| default topic | The topic an agent joins automatically on registration, taken from the declaration in the project configuration file, or, when there is none, from the normalized result of the workspace git repository's `origin` address; when neither exists, no topic is joined automatically. |
| public topic | A topic whose name and description propagate to every Broker in the connected network. A topic that is not declared public is confirmed to exist only by two Brokers that both have members in it. |
| project configuration file | The configuration file in the workspace, committed along with the repository, declaring the project's topics and whether to join them automatically. |
| roster | The list of all agents on one Broker that belong to a given topic. |
| pairing | The process by which two Brokers authenticate each other with a pairing key and save each other's identity. Once pairing completes, the two are peers. |
| peer | Another Broker that has completed pairing with this Broker and has not been unpaired. |
| pairing key | A secret shared by both sides of a pairing that proves identity during pairing; it is either a one-time pairing key or a pre-provisioned static key. |
| one-time pairing key | A pairing key that a Broker generates, is valid for a limited time and becomes invalid after one use. |
| pre-provisioned static key | A pairing key that can be determined before the system is deployed and written into a Broker's configuration file by the user or an administrator; it is reusable and does not expire, and the system does not generate it. |
| fingerprint | The digest of a Broker's public key; it is the Broker's identity and does not change after generation. |
| alias | A Broker's display name, appearing after the `@` in an agent address. When a Broker's self-reported alias is unconfigured, the system Broker takes the first segment of the system hostname (the part before the first `.`), and the user Broker takes the first segment of the hostname, a `.` and the owning account name in order; the alias is independent of the listen address, the listen port and the advertised address, and when it exceeds 24 characters the hostname part is shortened first, then the account name if it is still too long. |
| local alias | An alias this Broker gives a peer that is valid only on this Broker. For a peer with a local alias, this Broker uses the local alias in place of the alias the peer self-reports. |
| listen address | The address a Broker actually binds and accepts connections from other Brokers on, given by configuration or a startup parameter. An empty host part means every local address. A Broker whose listen address is empty does not listen and can only connect out to other Brokers. |
| degraded run | The running state in which a Broker does not exit after a startup step fails, keeps its local socket and reports the fault. When only the listen address cannot be bound, local features keep working, called local only; when the data directory or audit log is unavailable the Broker offers diagnostics only, called diagnostics only. If the failed step later succeeds on retry, the Broker recovers without a restart. |
| local only | One degree of degraded run: the only failure is that the listen address cannot be bound, so local agents' registration, listing, topics and messages keep working, pairing key generation fails, and peers cannot connect in. |
| diagnostics only | One degree of degraded run: the data directory or audit log is unavailable, so the local socket answers only handshakes and status, registration receives a refusal event, and other calls return `broker_degraded` with a reason. |
| offline | A state a Broker saves in its configuration: it refuses messages from peers, while links, membership and the directory keep working, and messages between local agents and messages sent to peers are unaffected. The opposite state is called online. |
| advertised address | An address a Broker publishes for other Brokers to connect to it, each item carrying a kind that determines how that item connects to the Broker; the only kind so far is direct, made up of the item's host and port. All advertised addresses in order form the advertised address list. What a card carries, and what an acceptor tells a dialer, is the whole advertised address list. Advertised addresses are used for connecting, display and telling apart several Brokers on one host, and do not take part in identity. A Broker that does not listen has an empty advertised address list. |
| link | A long-lived connection between two Brokers that are peers. There is one per pair, established by the dialer and re-established after a disconnect, carrying bidirectional communication once established. |
| dialer | The side of a peer pair that initiates pairing, responsible for establishing the link between them and re-establishing it after a disconnect. |
| acceptor | The side of a peer pair that accepts pairing; it does not connect out to the other side but waits for the dialer to connect in, and tells the dialer its advertised address list. |
| connected network | All Brokers connected directly or indirectly by links. |
| public Broker | A Broker that publishes its card and allows its information to propagate within the connected network. |
| broker card | The record a public Broker signs and publishes, stating its fingerprint, alias and advertised address list; the list may be empty. |
| directory | The set of all cards and public topic declarations a Broker knows. |
| reconciliation | The process in which the two ends of a link compare the records in their directories, add the records the other side lacks, and update the older ones. |
| name ownership | The rule that a name belongs to the account that registered it first. The owner's agent keeps an address without a disambiguator under that name; another account's same-named agent always carries the twelve-character disambiguator, and a bare name reaches only the owner's agents. A name no longer held is released after seven days. |
| name-owner table | The Broker's record of which account first registered each name and when the name was last held, persisted in `name-owners.json` in the data directory and bounded per account and in total. |
| alias tombstone | An effective alias that a peer has abandoned in the current peer relationship. It resolves to no peer but still counts as taken when alias conflicts are judged, and it is stored in the peer entry's `retired_aliases`. |
| unknown-account bucket | The single bucket that holds every uid with no account entry. Its uids share one per-account quota, so a rootless container rotating subuids cannot multiply a per-account limit; a lookup that fails or times out is refused and does not enter the bucket. |
| shared quota | A per-account quota shared among several callers instead of granted to each, as every uid in the unknown-account bucket shares one per-account quota. |
| admission connection limit | The fixed caps on the local connections a Broker admits: at most 4096 local connections at once, of which at most 64 are admitted to wait on an account lookup, each for at most 5 seconds. |
| directory receive limit | The cap on the directory records a Broker accepts: the records accepted over one link may not exceed `directory.max_records_per_link`, and the total may not exceed `directory.max_records`. |
| lookup tag | The value computed from a pairing key, the initiator's nonce and the initiator's fingerprint, by which an acceptor identifies which key the initiator used. |
| fingerprint warning | A warning that a directory card for a candidate address lists a fingerprint different from the paired Broker's. It marks that cards are self-reported, so the fingerprint is confirmed with the other side before the link is relied on. |
| self-reported card | A broker card whose content its publisher reports about itself and other Brokers cannot verify, so a value it carries, such as a fingerprint, is confirmed with the other side before it is relied on. |
