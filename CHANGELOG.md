# Changelog

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Added

- `create_pairing_key` and `peers key create` append a paste-ready connect prompt that already names this Broker's addresses and the one-time pairing key: one sentence to paste into a session on the other host, and the equivalent `peers broker connect` command. It lists every shown address and says to choose one the other host can reach, while the command uses the first address and offers the rest as replacements. The tool returns the same text as `connect_prompt`, and leaves the field out when no address can be shown.

### Changed

- `list_brokers` and `peers service status` now explain a peer whose link was closed because it sent more state frames than this Broker's inbound limit allows on one connection, instead of leaving the status detail empty. The detail says the peer ran past the state-frame limit, that the link reconnects after a backoff, and to check the audit log's `link_down` record. Other link failures that had no explanation keep none.
- `pairing.max_attempts_per_minute` now limits the unmatched pairing requests from each source per minute rather than from all sources together, a breaking change: one IPv4 address or one IPv6 /64 may make that many, and all sources together may make ten times that. Existing configurations keep their value; each source now gets its own allowance under the shared global ceiling.
- The link protocol version is now 2, a breaking change: a Broker of this version cannot establish a link or pair with a v0.5.0 or earlier Broker, and a link attempt is reported as version-incompatible; for a link, the accepting side names the peer's version, while the dialing side only reports the incompatibility. The digest fields of `TopicDigests`, `Roster` and `RosterDelta` changed meaning because each digest now binds the sender's fingerprint; see the Security entry below.
- On a system Broker, an agent whose name belongs to another account now shows a full 12-character disambiguator instead of the shortest distinguishing prefix, a breaking change: a client that compares the disambiguator with the one Claude Code shows for the same session, or that expects the shortest prefix, sees a different value. A by-name address reaches only the agent of the account that owns the name, so the later account's same-named agent is reached only by its full address. Member entries gained the publisher's account and a ref-required flag, so every peer must run this version, matching link protocol version 2. `list_agents` gained an `account` field for display.
- The configuration file no longer accepts YAML anchors and aliases, a breaking change: an existing file that uses anchors fails to load until they are removed. Mappings or sequences nested deeper than 32 levels are now parse errors, and a file larger than 1 MiB is refused before it is parsed.
- `broker.advertise` and `broker.advertise_extra` now check each host as an IP address or a domain name this system can dial, a breaking change: a configuration that loaded before may fail to load until the host is corrected, for example one with a space or a slash, an IPv6 address without brackets, a wildcard address, or a domain label over 63 bytes. A fully qualified name may keep one trailing dot.

### Fixed

- A session now tells the model why a running local Broker refused it instead of reporting that no Broker is available. A registration stream the Broker ended with an error code passes the Broker's sentence and code through, so an account at its registration limit sees `quota_exceeded` with the Broker's explanation rather than `the system Broker is unavailable; ask the administrator to start it`. A socket that answered but closed the handshake is reported as a running Broker that refused the connection and may be at the account's or the host's local connection limit, and only a missing or refusing socket keeps the wording about starting a Broker.
- A system Broker's permission check that cannot take a slot within its budget is now refused with `quota_exceeded` and `Too many configuration access checks are running; try again shortly.` instead of `internal`, so a caller knows to retry rather than treating the Broker as broken.
- `list_topics` now returns a tool error when the Broker does not answer within the topic RPC timeout, the same ten-second bound `join_topic` and `leave_topic` apply, instead of leaving the call open until the connection or the process ends. A session polling the topic list could otherwise wait without bound on a Broker that stopped responding.
- `get_config`, `set_config`, `set_broker_online`, `list_brokers`, `disconnect_broker`, `create_pairing_key`, `list_agents`, `connect_broker`, `send_message` and `update_broker` now return a tool error when the Broker does not answer within a fixed bound, instead of leaving the call open until Claude Code's own timeout. The bounds are ten seconds for the tools that read or write a small local file, twenty for `list_agents`, thirty for `connect_broker` and `send_message`, and four minutes for `update_broker`. They do not follow `send.request_timeout` or `link.dial_timeout`, so raising either past its bound makes the tool report `Delivery unknown` or a `Not connected` result before the Broker finishes; that is expected. An `update_broker` timeout says the upgrade was either abandoned, leaving the running version unchanged (a replacement that had started is rolled back), or completed, leaving the Broker restarting with the new version, and how to check.
- A session that remembered more topics than the Broker's topic rate limit allows in one burst no longer loses the rest when it re-registers. After a Broker restart the account's sessions restore their topics at once, and a join past the rate limit was refused with `quota_exceeded` and dropped from memory, so the topic could not be restored again unless the user rejoined it. A quota refusal no longer holds up the topics behind it: the refused topic is deferred and the pass continues, so a topic stuck at the account's count limit cannot keep the topics that fit from being restored. The deferred topics are retried as a whole after each pass, for as long as the registration stays valid, with an exponential backoff from 250ms to 30 seconds and jitter clamped to that range so that sessions refused together do not retry in lockstep; the entry is kept when the connection ends, one warning per topic is logged after the first few failures, and a rejection for any other reason is still dropped. A restore now belongs to one registration rather than to the Register stream, so a revoked or replaced registration stops it and the next registration restores at once, and a join refused with `not_registered` keeps the topic instead of forgetting it. The topic count limit shares the same code, so it is retried at the same slow pace and recovers by itself once another topic leaves and frees a slot.
- The audit log no longer leaves a merge window in memory when its expiry timer fires a little before the wall-clock deadline. Such a firing expires nothing and used to leave no timer armed, so the window was written only on the next append or `Close`, or lost if the Broker was killed first. It now re-arms a timer for the remaining time and is written once the deadline passes, without waiting for another event.

### Security

- Pairing attempts are now limited per source, so a stranger cannot fill one global counter with junk requests and keep a static-key pairing answering "try later". Each source, one IPv4 address or one IPv6 /64, may make `pairing.max_attempts_per_minute` unmatched requests per minute, and all sources together may make ten times that, which a party that can send from many sources, such as a whole IPv6 prefix, can still fill. A lookup tag is now bound to the initiator's certificate fingerprint, so the acceptor recomputes it with the fingerprint it sees in this TLS connection, and a party that forwards someone else's tag matches no key and consumes no one-time key. The initiator sends its alias in `PairConfirm`, after it has verified the acceptor, so a wrong or hijacked address no longer learns the host and account name, and the acceptor records no alias in a failure before the initiator's proof verifies. The pairing frames changed meaning and the link protocol version is now 2, so a Broker on an earlier version cannot pair with this one. Against an earlier Broker the failure is asymmetric: a new initiator that reaches an earlier acceptor is told `pairing key is invalid`, because that acceptor does not know `PairRequest`'s version field, while an earlier initiator that reaches this acceptor reports `protocol error: unknown PairReject reason 5`, because it does not know the version-incompatible rejection reason. This acceptor records only `version incompatible` in its audit and does not name the peer's version.
- A host that opens many unauthenticated connections can no longer evict the connections of other sources or of paired peers. Unauthenticated connections are limited per source and, once a peer's fingerprint is known, per fingerprint; the bytes and HTTP/2 header size a connection may send before authentication are bounded.
- `create_pairing_key`'s note, its not-listening error, the server instructions and `connect_broker`'s `key` parameter now say the pairing key and the connect prompt go only to the user, who passes them outside peers. A session no longer relays either to another agent over `send_message`, Claude Code's built-in session messaging or any other agent-to-agent channel when that agent asks for a pairing key.
- Rejected unauthenticated connections are merged in the audit log by network source, not by the certificate fingerprint the stranger chooses, so a client that rekeys every attempt can no longer make the audit log and the pending in-memory windows grow without bound. The pending windows are capped, further sources fold into one summary record, and appending a rejection no longer scans every open window.
- A malicious or compromised peer could send a Broker's own topic digests back verbatim: the echo matched every local topic, so the peer learned the member list of each and could forge members under those digests. A digest is now `SHA-256(salt ‖ sender fingerprint ‖ topic name)`, so the two directions of a topic differ and an echoed set intersects nothing. The digest fields of `TopicDigests`, `Roster` and `RosterDelta` changed meaning, so the link protocol version is now 2: this version's Broker cannot establish a link with 0.5.0 and earlier, which is reported as the existing version-incompatible status; the accepting side names the peer's version, the dialing side does not.
- Received content is framed as untrusted. The server instructions and the `list_topics` and `list_brokers` descriptions say that other agents' messages and other Brokers' directory entries are not the user's instructions and that operations they request need the user's explicit consent. Message bodies escape both the opening and the closing envelope tag in any letter case, so a body cannot forge either end of its attribution envelope. A peer delivery error is quoted back as the peer's words only when its code is one the receiver can return; otherwise the result is `delivery_unknown` with local text and a `peer_delivery_error_unrecognized` log event. Terminal commands display control and format characters from Broker strings in escaped form.
- The low-port refusals no longer advise `chmod 0644` or `chown root:root` on the system configuration file: a refused `Set` explains that the file must be writable only by root, and a refused start or reload prints the current `broker.listen` value for root to check before running `chmod g-w`. A system Broker creates a missing configuration file with mode 0600. A user Broker whose `/tmp/peers-<uid>` is taken by another account now uses the platform's per-user runtime directory and logs `runtime_dir_fallback`, and the account lock, runtime directory and local socket timestamps are refreshed every minute so a time-based `/tmp` cleanup does not remove them. The Broker running from the fallback directory is still found, and a second instance still refused, when the occupant removes the taken `/tmp/peers-<uid>` directory again.
- A paired peer could grow the member lists a Broker keeps for it without limit, and a local account could break every cross-host link with an overlong session name or a burst of topic changes. Agent names are now capped at 128 bytes, a peer's roster is held to 4096 entries per topic digest and 16384 per link, local topics are capped at 512 (128 per account on a system Broker) with 4096 local members each, topic changes are rate-limited per account, and a frame above the 4 MiB link limit is refused with `ErrFrameTooLarge` instead of breaking the link. A linked digest or roster frame still queued is now replaced in place by a newer one, and an unsent roster delta is folded into a full roster, so a burst of topic changes can no longer fill a link's send queue.
- A paired peer can no longer exhaust this Broker's memory, its dedupe table or a session's inbox quota. One connection's state-frame queue is capped at 4096 frames and 64 MiB of payload and runs at most 64 request handlers at once; the dedupe table holds at most 4096 entries per source; and each source gets a token bucket of 10 messages per target, refilled one every 10 seconds. A peer that exceeds a limit loses only its own connection, entries or quota; other peers and local sends are unaffected.
- Release builds no longer restore an Actions cache. The tagged release job verifies the module graph before goreleaser builds the binary a system Broker installs, and the site and real-session jobs build from source as well. Every third-party action is pinned to a commit SHA, `make lint` rejects a mutable tag, and every checkout leaves no credentials in `.git/config`. `make third-party-check` compares each vendored library with its recorded upstream and local changes, and `make vulncheck` scans the module graph on Linux and macOS.
- `golang.org/x/net` is upgraded from v0.60.0 to v0.62.0, which closes GO-2026-6866 and GO-2026-6860. Both sit in the `html` package, which peers does not call, so neither was reachable, but a release closes every known issue in the module graph.
- An alias that a peer gave up during a relationship stays reserved for that peer instead of becoming available to another peer, so an Agent address handed out earlier cannot start naming a different Broker.
- Self-reported aliases and addresses are validated and normalized before they are stored.
- A system installation no longer hands an existing group's members management of the system Broker without the administrator's knowledge. When the default `peers` group already lists members, was not created by an earlier peers installation and a new configuration file would be generated, `service install --system` refuses before writing any file unless the administrator names the group with `--admin-group`; a group whose id is 0 is refused outright, since its accounts would hold the configuration file's permissions. The member list includes accounts whose primary group is that group and, on macOS, nested groups, and a failed member lookup refuses the installation instead of treating the group as empty; naming the group or keeping an existing configuration file skips the lookup. The install summary names the administration group, where it came from and the members the account database lists.
- The install script no longer follows a symlink placed in a completion or man-page directory: it checks each directory from `/usr/local` down to the target before creating any of them, refuses a symlink, an owner other than root or `SUDO_USER` and group or other write permission, and skips the file with a warning and the command to install it by hand. A completion is written through a temporary file in the same directory and renamed into place, and when that directory belongs to `SUDO_USER` the account performs the temporary file's creation, write and rename through `sudo -u`, so a process of the account cannot swap it for a symlink and have root write through it.
- A peer could push records in a `Records` frame without being asked and pile up one fetch goroutine per `RecordList`. Each peer now has at most one outstanding `RecordRequest`; a `Records` frame is accepted only for identifiers this Broker requested within the last 60 seconds, each identifier is accepted once, and unrequested records in one frame are dropped together and reported as `directory_unrequested_records`.
- A peer could make every Broker in the network rewrite its directory file and keep forwarding records by issuing a new version of the same record. A replacement received from a link is now accepted at most once every 60 seconds per Broker, and a newer version that arrives inside the window is fetched once the window ends instead of waiting for the next reconciliation. Records accepted from a link are written once a minute by the maintenance loop instead of on every batch; records accepted within the minute before a crash are recovered by reconciliation. The window also applies to an identifier whose record expired and was purged, so a short-lived record cannot bypass it.
- A public topic whose name or description breaks the format rules and a card address that is not a well-formed host and port are no longer listed, while the record is still accepted and forwarded.
- A public topic's description declared by this Broker or a peer can no longer be replaced by a remote publisher that claims the largest version. The local interface reports the Broker whose declaration supplied the description, how many Brokers declare the name, and the declarer's alias.
- The fingerprint mismatch warning now says the directory card is self-reported and asks the user to confirm the fingerprint with the other side, rather than presenting the card's claim as fact. One card yields one warning and a Connect result carries at most eight.
- A local account can no longer exhaust a system Broker by opening many local connections, streams or registrations, by making it spawn permission-check processes without limit, by forcing an account-name lookup on every connection for a uid with no account entry, or by registering a session name without an upper bound. Local connections and `Register` streams are capped at 256 per account, 4096 connections at once across all accounts, and concurrent streams at 64 per connection; permission checks run at most 8 at a time and 2 per account; and a registration's downstream events are coalesced and bounded, with their backlog ending the stream with `quota_exceeded`. The connection handshake lets a uid already cached as a real account take its global slot without waiting for a lookup, and refreshes an expired entry in the background instead of pushing the account into the queue. Other connections wait for a lookup under a separate bound of 64, so socket connections arriving faster than getent answers cannot fill the global slots; a connection past the bound is refused at once, and a lookup that cannot start or finish within 5 seconds refuses the connection (fail closed). Uids with no account entry share one unknown-account bucket for every per-account limit, so a rootless container's rotating subuid cannot multiply a quota; only a definitive "no such account" enters that bucket and the cache, for 30 seconds, and a lookup failure or timeout refuses that request alone instead of being cached, so the next connection asks the account database again. Real accounts and uids with no entry are cached separately: the real-account cache grows only with the accounts the host has, while the negative cache is bounded at 1024 entries and evicts the least recently used one, so a rootless container's rotating subuid cannot evict a real account's cached name. Caller-name and permission-check lookups share one process-wide gate of 4 getent processes. Over-limit refusals and `access_check_busy` are logged at most once per account or uid per minute, and `access_check_unknown_account` at most once a minute across every uid, so that throttle keeps no entry per uid. The degraded diagnostics-only service applies the same connection, stream and registration limits. The systemd unit of a system Broker now sets `TasksMax=8192` and `LimitNOFILE=65536`; `peers update` writes the new unit when it rewrites the main unit, so the running service picks it up without a reinstall, and `sudo peers service install --system` writes it again.
- On a system Broker, one account could intercept or impersonate another account's agent when both used the same name. The Broker now records which account owns each name in `name-owners.json`: the account that registers a name first keeps its address without a disambiguator, a by-name address resolves only to that account's agents, and an agent of another account with the same name shows a full 12-character disambiguator, so the owner's short disambiguator cannot select it. An idle name is released after 7 days. A refused by-name send returns `not_found` and says the name belongs to another account. `list_agents` shows each agent's account, for display only.
- The self-update download now bounds `checksums.txt` on its own instead of sharing the archive's 100 MiB cap, and reads it line by line, so a checksum file far larger than a release needs cannot make the updater allocate memory out of proportion to it. A file above the new 64 KiB cap is refused with a size-limit error, and so is a single line above 1 KiB. A release API response is now checked against its 1 MiB cap before it is parsed, so an oversized response is reported as a size-limit error instead of a JSON decoding error. `checksums.txt` comes from the release's asset address on GitHub over HTTPS, and the API request goes to `api.github.com`, so exploiting either path needs control of the release source or of the HTTPS connection; both checks are defense in depth.

## [0.5.0] - 2026-11-21

### Changed

- The command line has been rebuilt on cobra with a noun-and-verb command tree, a breaking change; the old command names have been removed with no aliases. The commands map as follows:

  | v0.4.0 | v0.5.0 |
  | --- | --- |
  | `peers broker` | `peers service run` |
  | `peers status` | `peers service status` |
  | `peers audit` | `peers service audit` |
  | `peers offline` and `peers online` | `peers service offline` and `peers service online` |
  | `peers config get` with no key | `peers config list` |
  | `peers pairing-key create` | `peers key create` |
  | `peers peer list`, `peers peer connect` and `peers peer disconnect` | `peers broker list`, `peers broker connect` and `peers broker disconnect` |
  | `peers service uninstall` | `peers service remove` |

  Help groups the commands as Pairing, Local Broker and Installation. A usage error, including an unknown command, an unknown option and the wrong number of arguments, exits with code 2. Updating a v0.4.0 installation to v0.5.0 rewrites the service definition in the new command's format before the Broker restarts, so users do not need to reinstall it.
- Every `service` subcommand accepts the mutually exclusive `--system` and `--user` flags. With neither, root acts on the system service and every other account on its user service, which is the rule the install script uses; `service install --admin-group` requires `--system`. `service start`, `stop` and `restart` now accept `--system` instead of rejecting it, and every command that selects a level honors it and names the level when the service is unavailable.
- `peers update` and `peers uninstall` ask for confirmation only when standard input is a terminal, and fail with a message telling the user to pass `--yes` when it is not. `--yes` skips the questions and keeps the data; `--purge` removes the data without asking about the data, and still needs `--yes` when standard input is not a terminal. A non-root account whose host has only the system installation is shown the complete `sudo peers uninstall [--purge] --yes` command when it cannot be prompted, and at a terminal it is still asked whether to rerun the command through sudo.
- The install script reports how the installed version relates to the binary it replaced, before the service summary: `Upgraded from <version>.`, `Downgraded from <version>.`, `Reinstalled peers <version>.` or `Replaced peers <version>.`. Declining `Upgrade the system installation? [Y/n]` leaves the system installation unchanged, exits 0 and no longer suggests a user install.
- Tool errors from the MCP server end with `(code: <name>; reported by Broker <fingerprint>)` when the Broker reported them; an error without a reporting Broker keeps `(code: <name>)`.

### Added

- Shell completion for bash, zsh, fish and powershell: `peers completion <shell>` prints a script, and the commands complete Broker aliases and fingerprints, configuration keys and shell names dynamically. The install script installs the bash and fish completions, and the zsh completion in a system install; a system install writes them under `/usr/local/share`, and a user install writes the bash and fish completions under `$HOME` and prints how to enable the zsh completion manually. The fish completion is installed only when fish is present. If a completion cannot be written, the script prints a warning and continues, and `peers uninstall` removes the completions the install script wrote.
- Man pages. Every release archive contains them under `man/`, a system install copies them into `/usr/local/share/man/man1`, and `peers uninstall` removes the `peers.1` and `peers-*.1` pages it wrote.

### Fixed

- On macOS, the account-helper for an account in more than 16 groups failed to start, because Darwin caps `setgroups` at 16 groups, and every session of that account saw `not_registered`. The helper now starts as root and switches to the account's identity in the child with `setgid`, `initgroups` and `setuid`, as the access check already does, and the session registry watch recovers with it. A helper that fails to start or stops responding now reports its own reason, `the Broker's helper for this account failed to start or stopped responding; ask the administrator to check the Broker log`, instead of the message that no Claude Code session record matches the session's inbox socket.

## [0.4.0] - 2026-11-21

### Changed

- The project is renamed to `peers`, a breaking change. The binary, the release archives and the entry inside them, the Go module path, the installation paths, the configuration, data, log and runtime directories, the service unit names, the launchd label, the administration group, the project configuration file name, the environment variables and the pairing protocol labels all use the new name. See [ADR-rename-peers](docs/adr/adr-rename-peers.md). The MCP server name `peer` and the tool names are unchanged. peers is incompatible with agent-peer 0.3.0, and no migration is provided.
- When the user asks to send a message to every agent or to broadcast and does not mention peers, the session sends it to this host's sessions through Claude Code's built-in session messaging and then gives one short hint that peers can notify agents on other hosts. The session sends to every agent that `list_agents` returns, once per agent, only when the user explicitly asks for a peers broadcast, and a session without the built-in tool reports that a local broadcast is unavailable instead of sending through peers.
- After a self-update, the installed binary rewrites the service definition in the new version's format before the Broker restarts, so an update still leaves a working service when the service unit format changes between releases. If the rewrite fails or times out, the update restores the previous binary and the service definition and leaves the Broker running.

## [0.3.0] - 2026-11-20

### Added

- `--user` for the install script: it installs the binary and the user-level service for the account that runs the script without asking for the installation level. `--system` and `--user` both skip the question; the script refuses `--user` when it runs as root.
- `agent-peer uninstall` removes the service, the binary, the runtime directory and the account's MCP registration, and asks once before also removing the configuration, identity, audit and service logs; `--purge` skips the question. Root removes the system-level installation, and another account with only that installation is asked once before the command re-runs itself through sudo. When the data is removed at the system level, the administration group is removed too, but only when the installation recorded creating it, or when an older installation's configuration file uses the default `agent-peer` group; the binary is removed only when it is the running executable.
- `join_topic` and `leave_topic` accept an omitted `name` and then act on the session's default topics: the topics named by the project configuration file, or the one named by the workspace's git origin. These calls ignore the automatic-joining switches, so a session whose Broker or project file turns automatic joining off can still join its default topics on request. A session with no default topic gets an `invalid_argument` error that says to pass a name. Leaving the default topics only affects the current session; a new session joins them again when automatic joining is on.
- An `--allow-degraded` option for `agent-peer broker`. A Broker started with it does not exit when, after taking the account lock, the data directory or audit log is unusable or the `broker.listen` bind fails: the first keeps the process running with a diagnostics-only local interface, the second keeps every local call except creating a pairing key, and both retry and recover without a restart. Other startup failures still exit. Service definitions written by `agent-peer service install` pass the option.
- `agent-peer service start`, `stop` and `restart` start, stop and restart the Broker service for the account that runs the command: root acts on the system-level service, any other account on its user-level service. A level without an installed service fails and names that level; an account that only has the system-level installation is told to run the command with `sudo`. `start` and `restart` wait for the local socket and exit with code 3 when the Broker runs degraded, printing the failure and the fix.
- `agent-peer status` and `agent-peer peer list` print the Broker's state before the sections. A degraded Broker shows its level, the reason and the repair command; an offline Broker says that messages from other hosts are refused and gives the command that accepts them. A Broker that serves diagnostics only prints just the degraded lines, and `agent-peer status` exits with code 1 without repeating the reason on standard error.
- The `list_brokers` result carries a `local` object with the connected Broker's `offline` state and, while it runs degraded, its level, reason and repair command. An older Broker leaves `local` out, which reads as online and not degraded.
- Session tool errors carry fixed text for `broker_degraded` and `broker_offline`. A degraded Broker's reason says the call cannot run until the startup failure is fixed; an offline peer Broker says the message was not sent, resending will not deliver it, and the other user can be reached another way.
- Broker offline mode. The `broker.offline` setting, the `agent-peer offline` and `agent-peer online` commands, and the `set_broker_online` tool switch a running Broker between accepting and refusing messages from other hosts. While offline, a delivery from another host is refused with `broker_offline` and nothing is written to a session; links, topic exchange, local deliveries and messages this Broker sends continue. The state is kept in the configuration file, survives a restart, and a configuration-file edit applies without one.

### Changed

- The install script now chooses the installation level when neither `--system` nor `--user` is given. It asks `Install system-wide (all accounts)? [y/N]` on the controlling terminal, or `Upgrade the system-wide installation? [Y/n]` when a system-level service is already installed; answering no to the upgrade leaves the host unchanged and exits 0 with a hint to pass `--user` for a user-level install. Root installs system-wide without asking, an account without a controlling terminal gets a user-level install, and a system-level choice from a non-root account reruns the script through sudo. Passing both flags is a usage error, and a host without sudo fails with a message that says to install sudo or use `--user`.
- A Broker that refuses a `broker.listen` port below 1024 now fails at the listen step and exits with code 4 (listen address unavailable) instead of 5 (invalid configuration), a breaking change for scripts that match the old exit code.
- Without `--allow-degraded`, a startup failure caused by the data directory or the audit log now reads `the configuration is invalid: config: data directory or audit log unavailable: ...`, which names the failure class between the existing prefix and the file error. The failure class, exit code and behavior are unchanged.
- `agent-peer service install` now prints a summary after a successful or degraded installation: the install level and when the service starts, the binary, configuration file, run log and audit log paths, and the start, stop, restart and uninstall commands. When the installed service answers but its Broker is degraded, the command keeps the service installed and running, prints the reason and the repair command on standard error, and exits with code 3; other installation failures still exit 1.

### Fixed

- Runtime log records no longer carry the `event` key twice. A caller-supplied event name replaces the message, which moves to the `message` field, and audit failures name their kind under `audit_event` instead of a second `event`.
- Runtime log event values that were free text now use their snake-case names, so a value can be matched: `accountdb: account database lookup failed; falling back to os/user` → `accountdb_lookup_fallback`, `access check for an account outside the account database; denying` → `access_check_unknown_account`, `access check process reported an error` → `access_check_failed`, `account helper exited` → `account_helper_exited`, `account helper stderr` → `account_helper_stderr`. The config package logs `config_audit_before_load`, `config_audit_unknown_kind`, `config_audit_encode_failed`, `config_audit_not_open` and `config_audit_closed` in place of its `config: ...` messages, and keeps the audit event kind in `audit_event`.
- A system-level Broker no longer logs an account helper's exit as an error while the Broker is stopping. Such exits and their `context canceled` stderr lines are recorded below the warning levels and are not respawned.
- `agent-peer service install` checks the `broker.listen` address before it starts the service. An address already in use fails the installation with the address, the configuration file and the `broker.listen` key to change. When the address is held by this service's own running Broker, identified by the service manager's main pid and the local socket peer pid, the installation stops it and waits up to 20 seconds for the address, so a reinstall is not mistaken for a conflict; a foreign occupant fails the installation with the running service untouched. A failed installation never leaves a service that starts at boot or login: Linux disables the unit, and macOS removes the plist a fresh installation wrote or, when the plist existed before the installation, keeps it and disables the launchd label. The configuration file stays. If the service holding the address cannot be stopped, the installation still disables it and the error says it will not start automatically and gives the command that restores it. If the installation stopped an existing service before it failed, the error says `the existing service was stopped` and gives the command that restores it; on macOS that command loads the pre-existing plist the installation kept. The readiness timeout carries the last `startup_failed` reason from the service log, considering only records written after the installation began.
- A readiness timeout in `agent-peer service install` no longer reports only the silent socket when the service log has no `startup_failed` record from this installation. The error now includes the state and last exit status the service manager reports: `systemctl show -p ActiveState -p SubState -p ExecMainStatus agent-peer.service`, or `launchctl print <domain>/<label>`'s `state` and `last exit code`, and it says so when the query itself fails.
- On macOS, installing the service while it is running no longer fails with `Bootstrap failed: 5: Input/output error`. The installation boots the old job out once before the bootstrap, waits until `launchctl print` reports it gone and `broker.listen` is released, then bootstraps the new plist, retrying a bootstrap that still returns exit 5; the unload wait and the address wait share one 20-second budget, and the exit-5 retries have a separate 10-second budget. A failed replacement removes the plist a fresh installation wrote, or keeps a pre-existing plist and disables its label, so nothing starts at the next login; if the label cannot be disabled, the error says the service may start automatically. When the old service is gone, the error states that no Broker is running and gives the enable-then-bootstrap command that recovers it.
- A failed configuration write during `agent-peer service install` now names the configuration file it targeted.

## [0.2.0] - 2026-11-20

### Added

- Terminal commands for every Broker management operation: `agent-peer config get` and `agent-peer config set` read and change configuration, `agent-peer pairing-key create` creates a one-time pairing key, and `agent-peer peer list`, `agent-peer peer connect` and `agent-peer peer disconnect` list, pair with and unpair Brokers. Each command is authorized against the account that runs it, as the corresponding agent-facing tool is, and writes the same audit entries.
- Broker self-update, the `update_broker` tool and the `agent-peer update` terminal command. A Broker that runs under a service manager can be asked to install the latest official release: it downloads and verifies the release, replaces its own binary, replies, and exits so that the service manager starts the new version. The `update_broker` tool lets a session start this upgrade; Claude Code asks for confirmation before the call runs, unless the tool has been allowed in advance. The `agent-peer update` terminal command asks the selected Broker to update itself, and the Broker authorizes the request against the caller's write permission on its configuration file; the command replaces the binary locally only for a user-level Broker that does not run under a service manager, or when no Broker is running, after checking write permission on the binary's directory.
- A system-level admin group. Installing a system-level Broker creates the `agent-peer` group, which `--admin-group <name>` renames, and gives a newly generated configuration file root ownership, the group as its group, and mode `0660`. Members of the group manage the Broker without `sudo` when their account runs no user-level Broker; an account that also runs one uses `sudo` to reach the system-level Broker. The install script asks whether to add the installing account to the group and defaults to no; `--join-admin-group` adds it without asking. An existing installation keeps its configuration file unchanged: rerun the install script, or `sudo agent-peer service install --system`, to create the group, then run the `chgrp` and `chmod 0660` commands it prints. Skip that step when `broker.listen` uses a port below 1024, because such a Broker refuses to start while another account can write the file.
- An install script in every release archive. It installs the binary, installs and starts the Broker as a service, and registers the MCP server with Claude Code, for the account that runs it or, with `--system`, for the account that invoked `sudo`. Running it again is safe and does not register the MCP server twice.
- One-command online installation: `curl -fsSL https://github.com/wangzw/agent-peer/releases/latest/download/install.sh | sh` downloads the latest release for the platform, verifies it against `checksums.txt`, and runs the archive's install script. `--version <version>` installs a published version, and a system-level installation runs the same command with `sudo` and `--system`.

### Changed

- Installing a user-level or system-level service now generates a configuration file that lists every configuration item when no file exists: items with defaults are written with their values, items without a fixed default are shown commented out with an example, and each item has a one-line description. An existing file is left unchanged.
- `set_config` now replaces a commented-out placeholder for the key in place with the new value, instead of adding a second, active line elsewhere in the section.
- A Broker with no alias configured now derives its default alias from the hostname and the account that runs it: a system-level Broker uses the first segment of the hostname, such as `buildbox`, and a user-level Broker uses that segment followed by the account name, such as `buildbox.alice`. The default no longer depends on the listen port. A Broker upgraded from v0.1.0 without an explicit `broker.alias` therefore gets a new alias, and its agents get new addresses. To keep the old alias, read it before upgrading, from the `get_config` tool for `broker.alias` or from the part after `@` in the agent addresses that `agent-peer status` prints, and set `broker.alias` to it after upgrading. With the default port it is the full hostname followed by `-17443`, shortened to 24 characters, for example `buildbox-17443`.
- Brokers now check GitHub for a newer official release shortly after start and every 24 hours by default; `update.check` turns the check off and `update.check_interval` changes the interval. When a newer release exists, `agent-peer status` prints its version, and a tool result in each session ends with a one-line notice, once per session and version. The Broker never installs a release on its own; an update always starts from `agent-peer update` or the `update_broker` tool.
- A system-level Broker applies a `broker.listen` port below 1024 only when the configuration file is writable by root alone: a non-root caller cannot set such a port through the tools or a terminal command, a reload keeps the old value and writes a `config_rejected` audit entry, and the Broker refuses to start when another account can write the file.

### Removed

- The `AGENT_PEER_SOCKET` environment variable, a breaking change. A session and a terminal command now select their Broker by operating-system account alone: the user-level Broker running for the calling account if there is one, otherwise the system-level Broker if the account may use its socket. An account that also runs a user-level Broker reaches the system-level Broker with `sudo`. Setting the variable no longer affects the selection.

### Fixed

- Release bodies are now generated from the changelog. goreleaser did not load the extracted notes, so v0.1.0 was published with an empty body, and the body was added by hand afterwards.
- The README install steps now branch before moving the binary, so following the user-level and system-level paths in order no longer fails at the second step; the extraction step now uses an empty directory because the archive has no top-level directory.
- Writing the configuration file now refuses to follow a symbolic link: a symlink at the configuration path makes the write fail and leaves its target unchanged.

## [0.1.0] - 2026-11-19

### Added

- Cross-session messaging on one host: sessions that enable the agent-peer tools register with the local Broker as agents, and can list the agents visible to them and send messages to those agents.
- A user-level Broker that serves one account's sessions, with at most one Broker instance running per account.
- Topics that limit which agents can see and message each other, including a default topic derived from the project configuration file or the workspace's git origin so that sessions in the same project share a topic without extra steps.
- Broker pairing with one-time pairing keys and reusable static keys, direct links that the dialer re-establishes after a drop, cross-host message delivery, and an outcome-unknown result when a delivery request may or may not have been processed.
- Broker cards and public topics, which distribute public Brokers and public topics through the connected network while a private Broker stays unknown to Brokers it is not paired with.
- Reading and changing Broker configuration through the MCP tools, subject to the same file permissions as editing the configuration by hand, and an audit log of the changes.
- Terminal commands `agent-peer status` and `agent-peer audit` for viewing Broker status and the audit log on the host.
- A system-level Broker that serves the sessions of multiple accounts, and installation of a user-level Broker as a service that starts at login or a system-level Broker as a service that starts at boot; uninstall stops the service before removing its definition and keeps configuration, identity and audit logs.
- Handling of incompatible protocol versions on both the local interface and links: a tool call fails with a prompt to restart the Broker when the calling session's MCP server process and the running Broker use incompatible local protocol versions, and when two Brokers use incompatible link protocol versions the accepting side rejects the connection while the dialing side backs off and shows the reason when listing Brokers.
- Release archives for macOS and Linux on amd64 and arm64, with SHA-256 checksums.
